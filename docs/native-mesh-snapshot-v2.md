# Native mesh v2 discovery snapshots

## Response forms

Every request requires the shared bearer token. `GET /v1/native-mesh/agents` without query parameters uses the original legacy list: it returns `{ "agents": [...] }` for at most 100 records and at most 2 MiB, or 413 rather than a truncated list. This route is distinct from the parameterized snapshot scan below.

A first request with `?limit=100` reads and validates the entire registry in one SQLite read transaction. If the complete encoded `{ "agents": [...] }` response is strictly less than 2 MiB and contains at most 10,000 records, it returns that unversioned response in one piece. There is no `version`, `nextCursor`, or `revision`, and no continuation is needed. This path does not reuse an existing snapshot. If either boundary is exceeded, it falls back to a v2 first page instead of truncating the list. Both outcomes remain subject to the snapshot record and accounted-memory limits below. The initial `limit=100` scan checks a one-second time budget during row iteration, including when it falls back to v2. It also checks immediately before and after constructing a complete legacy response. A failed check returns 503. This is not a general cancellation guarantee: blocking operations and v2 page construction are not interrupted by a timer.

For a first request with `?limit=N` where N is 1 through 99, the server returns v2 directly. It reads and validates the complete registry in one SQLite read transaction, ordered by ID, or reuses an immutable snapshot created less than 10 seconds earlier. V2 responses have `{ "version": 2, "agents": [...], "nextCursor": ..., "revision": ... }` and contain at most N records and 2 MiB per page. A snapshot reused by different page limits contains the same saved data. Each row includes its saved `lastHeartbeatAt`; these values can be stale by the cache age plus the initial build time. No snapshot timestamp is added on the wire. Observations are not proof of current liveness.

A separate persistent topology revision is read in the same transaction as the rows. Database triggers increment it on insert, delete, and changes to ID, host, agent, parent, name or state. A pure heartbeat timestamp update does not increment it. Each reused first page and continuation checks the topology revision in a short read transaction. A mismatch prevents reuse or returns 409, respectively. Thus an identity or family change observed before that check cannot silently reuse the old snapshot; a new scan reads a fresh one. A change after the check can still race with the response and later delivery. The old discovery protocol also has a discovery-to-delivery time-of-check/time-of-use race. Family filtering remains a compatibility convenience, not strong authentication or atomic authorization.

Schema migration is additive: it creates `native_mesh_topology_revision_v3` and insert/update/delete triggers, and preserves the existing `native_mesh_revision_v2`. Existing old-version SQL writes to the same intact table will also fire the triggers; the old server ignores the new revision. A rollback to the old binary leaves these objects in place. Removing them is a separate maintenance operation that must not occur while new servers depend on them. This does not defend against a privileged writer dropping triggers, tampering with the revision, or restoring an older database behind running instances. Revision overflow fails the triggering write rather than wrapping. Review persistent schema changes and backup/rollback separately before any deployment.

For v2 only, if `nextCursor` is non-null, continue with the returned `revision` and `nextCursor` as `revision` and `after`; keep the same `limit` for that continuation chain. A null `nextCursor` ends the scan. A `limit=100` continuation is v2, not a new legacy scan. The numeric revision is an opaque random snapshot identifier, not a database revision or a credential. Each request is authenticated again. Only an `after` cursor actually issued for this snapshot is accepted. Malformed, repeated, unknown or inconsistent query parameters return 400. Topology-changed, missing, expired, restarted, or other-instance snapshots return 409; restart the entire scan. Route all pages of a scan to one instance. Shared bearer authentication does not distinguish individual accounts or prevent one holder from impersonating another; this change does not add such isolation or change family/message authorization.

A snapshot has a fixed 30-second lifetime from creation, not renewed by page requests or reuse. A scan that reuses an older snapshot has less time to finish. At most four multi-page snapshots and 24 MiB of accounted retained memory are allowed per API instance. Each scan is limited to 20,000 records and 8 MiB of accounted memory. Accounting uses twice the UTF-8 JSON bytes plus 256 bytes per row (including the ID index and a fixed worst-case allowance for 100 cursor bitmaps); actual runtime heap and transient SQLite/response allocations are not exactly measured and can be higher. Single-page scans are not retained. A limit breach returns 413; exhausted concurrent/aggregate capacity returns 503. No scan is silently truncated. The parameterized snapshot scan validates every stored row; malformed data fails the scan. The four-snapshot count limit is checked before starting a new scan, including a `limit=100` scan that would otherwise return the complete legacy response. Capacity and TTL may require operational tuning for a given registry, but must remain bounded. Slow scans can expire. Distinct generations count against the limits until expiry, including after a scan completes, to allow retrying a final page. Reuse reduces normal load, but an authenticated caller can still help exhaust capacity.

Existing message send, pull, and acknowledgement behavior is unchanged. The SQLite transaction is not held over HTTP requests. In WAL mode, a long initial scan can still temporarily retain WAL frames and consume CPU; production deployment should measure scan latency, memory and WAL growth with representative data. Using multiple API instances requires sticky routing for each scan, and process restarts invalidate its snapshots. Rolling upgrades involving old revision-based instances can also require scans to restart. Do not interpret a successful scan as authorization or proof of current liveness.

Compatibility note: clients using `limit=100` must accept either a complete unversioned `{ "agents": [...] }` first response or a v2 page and must not assume that every response to a parameterized request is v2. The v2 response shape is unchanged, but its revision is now an opaque process-local value rather than a persistent monotonic database revision. Changing `limit` midway or seeking an arbitrary well-formed ID is rejected unless that cursor was issued for that limit. The old client-side limits of 100,000 rows/32 MiB do not override the tighter server snapshot limits. Existing installations with a larger directory will receive 413 until limits or design are revisited; capacity must be measured before deployment.
