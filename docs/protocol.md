# 目标协议与系统交接设计

> **设计状态：目标方案，不是现有 API 的逐项说明，也不代表已实现或已通过跨公网验证。** 本文定义建议的协议契约及验收条件；路径和字段属于待实现的 v1 草案。具体安全方案、bootstrap 方式、传输选型以及平台覆盖仍需决策和验证。现有代码与本设计有落差，见文末。

## 1. 目标和信任边界

三位可信使用者管理分布在不同网络的机器与 agent。系统使 agent 能发现可用机器、自动取得已授权的 SSH 与无交互管理员能力、在机器上运行任务、保留 tmux 工作现场、与其他 agent 通信并共享资源经验。节点应尽量轻量；控制面与协议优先 Bun/TypeScript，并适配 Prime Agent 0.9.8；确有性能或平台需要时可用 Rust 实现组件。目标机器无需公网 IP，NAT 后可通过主动出站连接加入。HTTP 服务可监听 `0.0.0.0`，但监听所有地址不等于具备公网安全性。

这是小规模可信协作，不设计三人之间的细粒度权限隔离，也不声称隔离恶意成员。仍需保护共享凭据、网络链路、主机密钥、目标机器及审计日志：任何持有团队凭据的人应视为具备团队范围的高权限。禁止默认将明文 token 和控制面暴露到不可信网络；TLS、可信边界、秘密轮换和备份是运行要求，不是用户隔离机制。

## 2. 协议总体原则

- 定义版本化 JSON 控制面与带版本协商的双向数据通道。目标示例使用 `Authorization: Bearer <TOKEN>`，所有 secret 经安全配置传递，不放 URL、命令行或日志。网络使用 HTTPS/WSS 或经认证加密的替代传输。
- 对象使用稳定 ID；时间为带时区的 UTC，正文大小、编码、最大并发、重试期限均由版本化契约限制。未知字段策略、上限具体数值与协商机制待验证后冻结。错误返回 `{"error":{"code":"...","message":"...","retryable":false,"requestId":"..."}}`，不返回凭据、远端输出或堆栈。
- 修改请求带客户端生成的 `requestId`；重试同 ID 和相同内容返回原结果，不同内容返回冲突。读取不隐含消费；业务 side effect 使用持久化去重，不能将网络重试描述成 exactly-once。服务端应明确返回接收、完成、失败三个不同含义。
- 存储区分注册事实、近期健康、实际可用验证和通信消息。重启后持久数据可恢复，连接和内存状态须重新协商，不能将旧连接视作仍有效。

## 3. 注册与管理员能力契约

### 用户结果

用户发起一次注册，选择目标机器、SSH 用户、操作系统和允许的引导方式。**注册成功**意味着被指定的每个 agent 使用它自己的实际身份，能经一个可用路径 SSH 登录目标并无交互执行管理员操作。只创建一条记录、服务器自己能登录或成功启动 bootstrap 都不是成功。若身份集合尚未知，不能宣称覆盖所有未来 agent；新增身份必须另行授权与验证。注册界面应报告当前阶段、每个身份的验证结果、错误及可恢复动作，不输出敏感材料。

目标命令或 UI：`envinhands register <machine>`；要求输入目标描述、已授权的 bootstrap 凭据来源及验证身份集。自动配权必须以机器所有者授权为前提；若缺少管理员引导通道或确认，不尝试绕过认证，返回需要用户操作。候选方案：通过已有 SSH 管理员会话、预装节点的本地管理员上下文、或平台受支持的安装引导；如何获取和轮换 bootstrap 凭据、远程提权方式和 Windows UAC/OpenSSH 设置待决。不得假设任意机器可无需已有权限而自动获取管理员权限。

### 建议状态机和接口

| 操作 | 目标契约 |
|---|---|
| `POST /v1/registrations` | 提交 `requestId`、机器元数据、待授权 agent 身份引用与 bootstrap 引用；返回 `202` 和操作 ID。不得把密码或私钥写进普通 JSON 日志。 |
| `GET /v1/registrations/{operationId}` | 返回阶段、每身份结果、可操作错误和完成时间；客户端断线后可继续查询。 |
| `POST /v1/registrations/{operationId}/retry` | 对可恢复失败重试，携带新操作请求 ID；不重复安装或扩大授权。 |
| `GET /v1/machines` | 默认返回符合当前验证有效性要求的机器，可显式请求待处理及失败状态；提供身份维度的就绪信息与更新时间。 |

状态：`pending`（已接受但未完成）→ `connecting` → `provisioning` → `verifying` → `ready`；任一阶段可进入 `action-required`、`failed`，中断后经恢复流程继续。状态及阶段日志需持久化；并发重试以操作代数或租约防止旧结果覆盖新结果。部分身份成功时仍不可整体报成功；应保留每身份诊断并支持幂等续跑。失败后是否回滚已成功配置、回滚失败如何提示，属于待决策略；无论如何不能静默删除既有用户配置。

验证必须经实际使用路径，以每个目标 agent 的真实身份执行 SSH 主机密钥校验、登录和非交互管理员探测。Linux/macOS 的权限检查可用受限、无副作用的 `sudo -n` 命令；Windows 应检查当前 SSH 会话的有效管理员令牌，而不是只看账户组成员。该检查不保证未来持续在线，状态应附带验证时间、身份和路径；TTL、主动复检和异常时降级阈值待决。服务器身份验证不能代替 agent 身份验证。密钥预置信任或首次信任的人工确认必须独立设计，禁止自动接受未知或变更主机密钥。

## 4. 多出口连接和故障回退

每台机器发布能力与可用出站路径；控制面管理带健康时间、失败原因和策略的候选集合。推荐优先次序只是初始方案，必须按可达性、安全策略和实测确定：

1. 直连 SSH（同网段、VPN 或已有可信路由）；
2. 双方可访问的现有私有网络或受控跳板；
3. 节点主动向团队可达的 relay 建立出站长连接，控制面通知节点创建通道，代理 SSH 的双向字节流；
4. 后续经验证的其他穿透或中继方式，不能预设所有 NAT 均可打洞。

不要求目标拥有公网 IP 或接受入站连接，但至少必须有共同可达的中继/网络基础设施与相应出站权限；零公网并不意味着无网络依赖。relay 的位置、是否自托管、TLS 和 DNS 配置待部署决策。

候选路径应记录握手超时、连续失败、退避和冷却；新连接自动尝试下一条路径，恢复后按稳定策略探测并恢复优先级，避免抖动。记录选中路径和可观察原因，供用户诊断。**不承诺透明迁移已建立的 SSH/TCP 流**：路径失效应明确关闭，通知上层重新连接；任务继续或恢复取决于 tmux 与应用幂等性。连接探测不可修改目标状态；重试需要上限、指数退避和抖动，禁止无限快速重试。

### Relay 建议线协议

控制连接和数据连接必须认证，所有节点及请求均带协议版本与稳定会话 ID。一个可行的握手序列：节点注册 `node.hello(nodeId, capabilities)` → 控制面确认 → 客户端请求连接目标节点 → 控制面签发短期一次性 channel 标识 → 节点建立 channel 并连接**本地配置的** SSH 端点 → 节点确认就绪 → 客户端获准发二进制帧。即使团队共享权限，也应限制 channel 指向节点明确配置的目标，避免把 relay 变成任意 TCP 代理。具体签发、防重放与证书/secret 生命周期待定。

就绪前只允许握手控制帧，就绪后使用二进制帧传送不透明 SSH 字节；端到端 SSH 负责加密和主机身份认证。协议需规定单帧/单会话缓冲、setup 和 drain 超时、并发上限、心跳和断连错误；上限待基准测试。写满时应暂停上游、有限缓冲或明确失败，绝不无限积压。WebSocket 不提供 TCP 半关闭：若实现不能可靠桥接半关闭，必须对调用方暴露该限制，不能将正常 close 当作远端已处理的确认。relay 重启或节点断开时所有受影响 channel 应清理，不伪造完成。暴露 `0.0.0.0` 的监听应由防火墙、TLS 和可信代理保护；监听地址本身不是认证机制。

## 5. Agent 发现、消息和资源经验

### 发现

Agent 启动后登记稳定 `agentId`、机器 ID、能力、协议版本和可选当前任务；定时心跳并附服务器接收时间。目录返回 `online` / `stale` / `offline` 应基于明确定义的租约，状态仅是近期观测，不保证 agent 当前可响应；TTL、时钟处理和心跳负载上限待决。重启或网络分区时 agent 重新登记，不依赖本地连接仍有效的假设。

### 通信契约

建议以 `POST /v1/messages` 发送 `requestId`, `from`, `to`, `type`, `payload`；成功区分 `202 accepted`（已持久接受，非已处理）和重复请求的原结果。`GET /v1/messages?to=...` 列出待处理消息；处理后 `POST /v1/messages/{id}/ack` 显式确认。相同 ID 不同内容返回 `409`。接收者可能重复读取、多个消费者可能并发处理；处理端须持久去重并保证副作用幂等。确认丢失、agent 崩溃和服务器重启均不得导致未经确认的消息静默丢失。多消费者的 claim/lease 是否需要，以及确认保留期、分页、顺序、消息体限制、过期与死信策略均待决；不承诺 exactly-once 或严格全局顺序。共享凭据下 `from` 只是声明，不是可审计的强身份。

### 资源经验

建议以资源 ID 为键提供结构化经验条目：作者、时间、适用环境、内容、来源及版本；支持查询、分页和追加，允许引用任务或消息。应标记经验的新鲜度和适用范围，不能把其他 agent 的经验直接当成事实或自动执行的指令。存储配额、归档、冲突合并和隐私清理策略待决。敏感凭据不得写入共享消息和经验记录。

## 6. 任务、tmux、恢复与轻量节点

任务协议应提供稳定任务 ID、目标机器和身份、命令引用/参数、工作目录、资源限制与生命周期状态。提交的成功只表示已接受；退出码、完成时间和错误是独立结果。避免把未经校验的用户输入拼接进本地 shell；远端执行的命令和信任边界需单独定义。

Linux/macOS 目标优先使用每任务或每工作区命名的 tmux session；网络中断或控制面重启后，通过稳定任务 ID 重新发现并 attach，而不是自动再执行一次。需明确 tmux 不存在时的安装/提示及会话清理策略。Windows 不应声称原生 tmux 可用：采用 WSL tmux 还是独立持久终端适配器待决，必须报告实际能力和降级；不能假装断线任务已保活。针对 agent 重启、节点断连和目标机重启分别定义恢复：tmux 仅有助于目标机和 tmux 仍存活的情况；主机重启后的进程恢复需额外机制，当前不作保证。

节点仅负责身份登记、出站连接、受限的本地连接桥接和必要探活，不要求在目标上运行完整 Prime 环境；依赖、内存、CPU、安装包大小和支持平台需建立基线和预算。与 Prime Agent 0.9.8 通过适配层接入，暴露可调用的发现、注册状态、远端任务、agent 消息和经验查询能力；以 agent skills 提供可复用的使用说明和安全约束。Prime 的真实接口与技能加载行为需在目标版本中验证，不预设当前 API 或兼容性。平台检测不支持时应提供明确错误，而非虚假成功。

## 7. 操作、安全和可观测性

- TLS 终止代理应保护控制面与 relay、正确处理 WebSocket upgrade、设置合理连接/请求限制并阻止后端绕过；`0.0.0.0` 只用于按需监听，默认部署应限制访问。Bearer 密钥通过环境或秘密管理器提供，轮换方案及断连重认证待决。禁止把密钥放到命令行、日志、错误或示例中。
- 记录无敏感内容的 requestId、operationId、阶段、身份引用、路径切换原因、错误码和耗时；时间戳由服务端生成。持久化需备份与恢复演练；保留期、日志脱敏、消息大小、速率与容量限制要在部署前确定。
- 失败设计以显式失败和恢复为准：代理不可达、管理员授权不足、主机密钥变更、旧 agent 身份撤销均不能产生 ready 假象。由于三人共享信任，团队应认识到凭据泄露等同于全部机器管理员权限泄露。
- 协作交付使用 `main` 和 Conventional Commits；不要求 CI。合并前运行并记录可复现的本地测试与手工跨平台验证。

## 8. 验收标准

以下是目标，不表示现已通过。测试须记录环境、版本、结果与限制：

1. **授权与状态**：在 Linux、macOS、Windows 的受支持组合上，从经批准的引导方式注册；每个指定 agent 用自身身份和真实路径成功 SSH 并无交互完成无副作用管理员检查，才返回成功。缺凭据、拒绝授权、host key 未知/变更、部分 agent 失败时，不能返回整体成功；重试不重复扩大权限。
2. **网络**：目标无公网 IP、禁止入站且允许出站时，经可达 relay 完成注册、SSH 与任务；直连失败时自动切换候选路径。模拟一条出口断开、恢复，记录有限重试与路径切换；已有 SSH 流明确断开，不能伪称无损迁移。
3. **消息**：发送方响应丢失后以相同 requestId 重试得到同一结果；相同 ID 不同内容冲突。多次读取可重复，业务端去重，处理成功后 ack；发送、读取、确认各阶段重启服务均不丢未确认消息。测试明确显示无 exactly-once 承诺。
4. **发现与经验**：两个不同机器上的 agent 能互相发现并交换消息；心跳中断后在约定期限变为 stale/offline；经验条目可写入、检索且保留作者和时间。存储重启后可恢复。
5. **会话恢复**：Linux/macOS 上启动 tmux 任务，断开控制连接并恢复后 attach 同一会话，进程不重复启动。Windows 按最终选定适配方案验证；未实现平台清晰报不支持。目标重启不误报任务仍在运行。
6. **协议资源边界**：覆盖鉴权失败、错误帧、握手超时、慢消费、缓冲上限、客户端/节点/relay 断开和半关闭；资源受限且错误可观察，无无限堆积，无虚假交付确认。
7. **集成与运维**：在 Bun/TS 和 Prime Agent 0.9.8 的真实运行环境验证 skills 调用，记录节点安装包、内存与资源预算；验证 HTTPS/WSS 代理、主机密钥、secret 不进入日志及备份恢复。跨公网测试若未执行，报告明确写未验证。

## 10. 开放演进：资源网络与自主协商

以下为可探索方案，不是首版承诺或已实现能力。设计应保留开放扩展空间，而不是把单个中心服务、单一 relay 或静态机器清单固化为协议前提。

### 跨团队资源网络与模型

可将机器、GPU、CPU/内存、磁盘、网络出口、SSH 身份、执行环境、工具、可恢复会话和 agent 能力统一抽象为带类型、稳定 ID、属性、状态和观测时间的资源。资源声明与实时可用量分开，支持能力描述和供应方定义的扩展字段。使用命名空间或签名的来源标识避免跨团队 ID 碰撞；版本化 schema 允许不同实现协商未知类型，而不是要求中心服务理解所有资源。可信三人场景仍可使用共享信任，不强制构建多租户权限系统。未来跨团队共享引入的信任、配额和责任问题应独立讨论，而非假设所有团队都互相信任。

多个控制域可通过联邦目录交换可发布资源摘要；本地仅暴露经配置允许共享的元数据。检索结果须带来源、更新时间、可信度及有效期，过期数据不能当成实时占用保证。可比较中心目录（简单、易运维但有单点）、联邦目录（自治但存在延迟和冲突）以及点对点 gossip（容错更好但需要发现与一致性治理）。协议需允许混合而不是提前锁定选择。

### 动态申请与 Agent 自主协商

Agent 可表达任务所需的操作系统、算力、内存、网络、地理位置、成本、持续时间及信任条件；发现候选后提出申请，资源持有方返回 offer、可用时间和约束。建议的生命周期为 `requested → offered → reserved → active → released/expired`，持久化操作 ID、租约与续期时间。申请超时不能推定分配失败；查询原 operation ID 再重试，以免重复占用。失联后租约到期释放，任务是否终止与现场如何保存需资源提供者明示；时钟偏差和分区下双重分配须以各资源的权威协调者裁定，不能依赖缓存目录。调度算法、计费、抢占、公平性与资源回收机制均待验证。

Agent 之间可基于机器可读能力交换任务意图、约束、候选方案、确认和结果，支持协商而不是仅发送自由文本。最终执行方应明确接受，超时和重复请求可追踪；不要把另一个 agent 的说明作为自动提权授权。经验可关联资源、任务结果、版本和证据，由接收方按上下文判断；可探索可搜索索引、版本演化和冲突标记，但不应将未经验证的推荐自动变成执行命令。

### 多传输、多出口与无中心降级

面向不同网络，可将直连、VPN、跳板、多个独立 relay、企业网络代理及未来传输实现为统一连接候选。按成功率、延迟、成本和策略动态排序；可探索探测并行、备用热连接和多出口聚合，但 SSH 单 TCP 流不能简单地在多条无序路径拼接：多路径需要有序重组、拥塞控制、去重与安全验证，否则只对新连接做回退。应实测出口受限、对称 NAT、代理和弱网场景，不能保证任意网络均可穿透。

中心不可用时，节点可继续运行已建立的本地任务和 tmux 会话；缓存的目录与经验只能标为陈旧数据，不能确认新租约或最新权限。已建立的点对点或备用 relay 通道可继续通信，若有独立的持久本地队列则允许排队并标识未同步；恢复后通过稳定 ID 去重、重放及冲突处理。没有可用协调者时，不应对共享独占资源伪造成功分配。可探索多控制节点或联邦故障切换，但成员变更、一致性、分区合并、凭据撤销及避免脑裂都需先验证；无中心降级不等于零基础设施。

### 扩展验收候选

在不同控制域之间同步经过批准的资源摘要，验证来源、过期和版本兼容；发起并续期资源租约，故障后确认不会重复分配；切断中心时验证已运行任务不被静默终止、缓存标注陈旧、恢复后消息去重；比较至少两种出口在失效及恢复时的行为。任何多路径聚合、联邦一致性或跨团队信任声明，只有相应故障测试成功后才能标注为支持。
