# Readiness refresh timing

Readiness is point-in-time SSH and administrator verification, not a heartbeat. The default SSH client connection timeout is 20 seconds; the complete SSH process has 45 seconds. The background refresh deadline is 50 seconds, and its stop deadline is 55 seconds. Windows uses the same limits. Existing `checkTimeoutMs` and `stopDeadlineMs` refresh options still override their defaults; an explicitly shorter outer timeout can cut off SSH early. OpenSSH may itself fail before the process deadline, including at its connection timeout.

A completed SSH check reports its elapsed process time. Refresh completion events include `sshDurationMs` when an SSH process ran. `timeoutStage` distinguishes the SSH process deadline from the outer refresh deadline. The SSH connection and remote command stages cannot be distinguished from these results: SSH output is not captured, so a nonzero SSH exit does not prove which stage failed. The opt-in refresh CLI prints completion timing and timeout stage without target IDs. These observations are not proof of a database commit: compare the stored state separately. A slow success is a successful observation at that time, not proof of stable connectivity.

The default schedule remains 120 seconds with 10% jitter and concurrency 3 (configurable up to 4). Cycles coalesce rather than overlap. A large fleet or many slow checks can therefore take longer than a schedule interval; the default readiness TTL remains 5 minutes. Existing ready evidence is retained during a check only until its original TTL and failed verification does not renew it. No interval/concurrency setting guarantees coverage within TTL for an arbitrarily large or slow fleet. Size the fleet and monitor observed durations and expiry; extending timeouts does not extend TTL. An observed expiry alone does not establish why a device was not ready.

Stop cancels queued work, aborts active checks, waits for draining, and does not accept a result after stop as ready. If stop reaches its deadline it rejects; keep storage open until in-flight work settles, then retry stop. No readiness value is set merely because a timeout changed.
